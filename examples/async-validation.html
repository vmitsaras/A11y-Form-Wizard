validationAdapter: {
  validateStep(context) {
    return context.data.sync_invite_code === "ACCESS-42"
      ? { valid: true }
      : { valid: false, errorTarget: codeInput };
  },
  focusError({ result }) {
    result.errorTarget?.focus();
  }
}

Accessibility evidence

Screen reader expectations

These are expected DOM, focus, and live-region behaviors—not universal announcements. Verify the final integration with the browser and assistive technology combinations your product supports.

Expected behavior by validation state
StateExpected exposed behavior
Native invalidThe dedicated polite live region announces the error count and first error, the visible error summary remains a non-live block, and focus moves to the first invalid control.
Adapter pendingThe form and initiating control expose busy and disabled states, the control keeps its accessible name while a visible “Validating…” label is shown, focus stays in place, and a polite status reports progress.
Adapter invalidThe adapter owns error markup and announcement; the wizard reveals the target step before calling focusError().
Operational failureThe wizard exposes one generic retry message and keeps focus on the initiating control.
Destroy during validationThe signal aborts, no stale result updates the wizard, all steps become visible, and the laboratory status reports teardown.

Native constraints always run before adapter rules. Adapter-invalid output belongs to the adapter; rejection, malformed results, and timeout messages belong to the wizard.
