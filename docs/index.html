Install

Add the package

Install the package, import the base stylesheet, then initialize one semantic wizard root. The package does not auto-initialize.

Install with npm

npm install a11y-form-wizard

Import and initialize

import { createA11yFormWizard } from 'a11y-form-wizard';
import 'a11y-form-wizard/styles.css';

const root = document.querySelector('[data-a11y-form-wizard]');

if (root instanceof HTMLElement) {
  createA11yFormWizard(root);
}

The install command reflects the intended package usage. Verify the package is published and reachable before a public launch.

Instructions

Use the plugin on a page

The wizard starts from meaningful form markup, then the module hides inactive steps, updates progress, validates native controls, moves focus, and announces changes.

1. Add the assets

<link rel="stylesheet" href="./dist/styles.css" />
<link rel="stylesheet" href="./assets/themes/a11y-form-wizard-theme-default.css" />

<script type="module">
  import { initA11yFormWizardAll } from './dist/index.js';

  initA11yFormWizardAll();
</script>

2. Initialize one wizard

import { A11yFormWizard } from './dist/index.js';

const root = document.querySelector('[data-a11y-form-wizard]');
const wizard = new A11yFormWizard(root, {
  preventSubmit: true,
  autoAdvanceChoice: false,
});

wizard.next();

Publishing workflow

  1. Edit source files in src/ and editable examples in examples/.
  2. Run npm run docs:sync to copy publishable files into docs/.
  3. Preview with npm run docs:serve.
  4. Publish GitHub Pages from the main branch and the /docs folder.

The static examples use placeholder form actions and prevented submissions. Production forms still need real endpoints and server-side validation.

Accessibility

Behavior you can verify

The plugin enhances meaningful form markup and keeps native control behavior. Test the result with the browsers and assistive technologies your product supports. The validator laboratory expectation table documents focus, busy-state, and announcement ownership for advanced validation states.

Semantics, focus, and status

  • Uses native forms, fieldsets, legends, labels, inputs, and buttons.
  • Focus moves to the active step heading after step changes.
  • Invalid fields receive focus and are associated with generated error text.
  • Progress, step changes, validation errors, and demo success are exposed as text.
  • Radio auto-advance is opt-in to avoid an unexpected context change.
  • Transitions respect prefers-reduced-motion, and states do not rely on color alone.

Keyboard interaction

Tab / Shift + Tab
Moves through native form and navigation controls in document order.
Space / Enter
Activates native buttons, radio buttons, checkboxes, and submit controls.
Enter on form controls
Uses native submission, validates all steps, and focuses the first invalid field.
Stacked step trigger
Uses a native button to reopen completed or current steps.

API

Methods, functions, and options

Public methods are intentionally small. Step indexes passed to JavaScript are zero-based; event details report human-readable one-based step numbers.

Initializes every [data-a11y-form-wizard] root and returns an array of instances.

  scroll: true,
  triggeredByChoice: false,
});

Review and edit

Review steps are author-provided markup. Map only native control names that are appropriate to repeat visibly, and use native edit buttons to return to a step. Password, file, hidden, and button-style inputs are excluded. Reset and destroy restore the original review content.

Async and external validation

Native constraints run first. A validation adapter owns its own invalid output; the wizard owns operational failures, pending state, and stale-result protection. Cancellation is cooperative, so adapter code must pass the provided AbortSignal to abortable work. External ownership must be selected when the wizard is initialized before connecting the validator bridge.

Markup

Markup contract

Keep native form controls in place. The data attributes identify plugin roots, steps, controls, progress text, error output, and lifecycle regions.

Minimal structure

<section class="a11y-form-wizard" data-a11y-form-wizard>
  <form action="/api/job-application" method="post">
    <progress aria-label="Form progress" data-a11y-form-wizard-progress></progress>
    <span data-a11y-form-wizard-current-step>1</span>
    <span data-a11y-form-wizard-total-steps>2</span>
    <div data-a11y-form-wizard-error-summary hidden></div>
    <div data-a11y-form-wizard-live aria-live="polite"></div>

    <fieldset data-a11y-form-wizard-step>
      <legend>Step label</legend>
      <h2 data-a11y-form-wizard-step-heading>Question</h2>
      <label data-a11y-form-wizard-error-container>
        <input
          type="radio"
          name="answer"
          required
          data-a11y-form-wizard-choice-input
        />
        Choice text
      </label>
      <button type="button" data-a11y-form-wizard-next>Continue</button>
    </fieldset>
  </form>
</section>

Themes and skins

Palette and layout

Load the base component CSS first, then one or more theme files. Select palette with data-theme, layout treatment with data-skin, and spacing with data-density.

Use a built-in theme

<link rel="stylesheet" href="./dist/styles.css" />
<link rel="stylesheet" href="./assets/themes/a11y-form-wizard-theme-dark.css" />

<section
  class="a11y-form-wizard"
  data-a11y-form-wizard
  data-theme="dark"
  data-skin="terminal"
  data-density="compact"
>
  ...
</section>

Included skins

Use editorial-split, bento, receipt, timeline, terminal, glass, brutalist, or mobile-sheet. Skins are CSS-only and do not change wizard behavior.

Events

Lifecycle events

Events bubble from the wizard root. Each event includes the plugin instance in event.detail.instance.

Listen for submission

document.addEventListener('a11y-form-wizard:submit', (event) => {
  console.log(event.detail.data);
});
Event reference
Event When it fires Useful detail
a11y-form-wizard:init Initialization completes. currentStep
a11y-form-wizard:step-change Active step changes. currentStep, previousStep, totalSteps, triggeredByChoice
a11y-form-wizard:choice-change A marked radio choice changes. currentStep, name, value
a11y-form-wizard:validation-error A required field or invalid value blocks progress or submit. currentStep, control, message
a11y-form-wizard:validation-start An adapter validation operation enters its single pending state. phase, currentStep, trigger
a11y-form-wizard:validation-end An adapter operation finishes or is cancelled. phase, status, currentStep
a11y-form-wizard:submit A valid form submission is attempted. data, nativeEvent
a11y-form-wizard:reset The instance is reset. instance
a11y-form-wizard:destroy The instance is destroyed. instance

Boundaries

Limitations

The plugin manages wizard behavior, not your complete form delivery or accessibility assurance process.

  • Markup is not generated automatically; authors provide the semantic form structure.
  • Production forms still require a real endpoint, server-side validation, security controls, and error handling.
  • Review mappings create another visible copy of selected values; omit sensitive mappings or provide static redacted text.
  • Remote validation, retries, authentication, privacy notices, and data minimization belong to consumer adapter code.
  • Adapter cancellation stops wizard updates immediately, but underlying work stops only when the adapter honors the provided AbortSignal.
  • The package does not auto-initialize on import.
  • Static demos prevent submission and use placeholder form actions.
  • Repository theme files support the demos; the npm package exports the base stylesheet.
  • Test target browser and assistive-technology combinations before release.
